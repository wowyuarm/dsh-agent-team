# 外部用户报告：0.1.1 → 0.1.5 升级后旧会话打不开（2026-09-10，Human 转述）

原帖环境：dsh 0.1.5-rc.1 / Windows 11 / Node v24.4.1。35 个会话里 15 个打不开，网页报
`failed to observe session ... refuses this format v0 Session`。

## 报告者归纳的四类拒绝（一次只报一个，修掉一个冒出下一个）

1. 老版本权限设置多出的 `origin` 字段，新版不认（新版已不用该字段，可忽略）。
2. 子代理记录 descriptor `version: 2`，新版只认 3（两种格式字段相同，可按 3 处理）。
3. **插件自定义消息来源类型**（如 `instruction-hint`、`at-file-mention`），新版不认。
4. `dsh-chat-import` 导入会话开头的 `session/imported` 标记，新版不认。

## 对本工作项的价值

- **与我们 B 类同构且同因**：第 3 类与我们的 `agent-team-context-handoff`/`-continuation` 是同一堵墙（`SOURCE_KINDS` 封闭白名单）。证明这是生态面问题——任何用过 `MessageSourceMap` 扩展的插件都被 0.1.5 拒绝，不止我们。
- **第 2 类 = 我们的 C 类**（descriptor v2，本机 35 例，Human 已裁决不管）——外部用户同样踩到，属上游修复责任。
- **上游报告弹药**：四类拒绝 + 报告者的诉求（「能忽略的忽略、能升级的升级，或至少给个修复命令」）与我们的选项③（上游契约：迁移目录插件注册点 / 官方修复入口）完全对齐。引用时附我们 0.1.10 的自愈实现作为「插件侧只能自救」的证据。
- **对迁移设计的工程警示**：拒绝级联一次只报一个错 → 我们按 API 报错分类的 artifact 可能**还藏着后续缺陷**（先例：`af855c4b` 的 E 类挡住了它的 B 类）。我们的设计已天然防住：transform 后的 catalog 全量内存校验会暴露所有缺陷，非我们种类的缺陷 → 记日志跳过，不产生半迁移状态；验收口径是迁移后真实 API 全量重读，被遮蔽缺陷无法漏网。
- 报告者的第 1/2/4 类属 harness 自有数据，不在我们的迁移范围（我们只修自己写的 source kind）。
